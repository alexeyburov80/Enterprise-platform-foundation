# Роадмап: модернизация ИТ-архитектуры предприятия

> Основа: раздел 6 ТЗ («Дорожная карта: фундамент + независимые модули»).
> Принцип: не жёсткая цепочка этапов, а один фундамент + пул независимых модулей,
> которые можно начинать в любом порядке и параллельно.

## Как читать этот документ

- **Фаза 0 (Фундамент)** — выполняется один раз, в начале, и блокирует старт остальных модулей
  (без шины и кластера подключать сервисы некуда).
- **Пул модулей** — не фазы, а независимые треки. Их можно вести параллельно, разными
  людьми/командами, в любом порядке. Ни один модуль не ждёт готовности другого — вместо
  недостающей зависимости поднимается заглушка (стаб-сервис с тем же API-контрактом).
- Оценки трудозатрат — ориентировочные (в человеко-неделях, ч/нед), для планирования ресурсов.
  Уточняются после аудита (первая задача фундамента).

## Фаза 0 — Фундамент (once, единый старт)

| # | Задача | Результат / критерий готовности | Оценка | Ответственный | Блокирует |
|---|---|---|---|---|---|
| 0.1 | Аудит БД, десктоп-клиентов, процессов бухгалтерии и табельного бюро | Карта текущего состояния: список БД, схем, клиентов, интеграций | 1–2 ч/нед | Архитектор + аналитик | Всё остальное |
| 0.2 | Единая модель сущностей (заказ, партия, станок, сотрудник, операция) | Согласованная схема данных, зафиксирована в docs/ | 1 ч/нед | Архитектор | Модули (частично) |
| 0.3 | Базовый k8s-кластер (мин. 3 узла) + CI/CD + мониторинг-скелет | Кластер принимает первые сервисы, pipeline «commit → deploy» работает | 2–3 ч/нед | DevOps | Всё остальное |
| 0.4 | Базовый RabbitMQ-кластер (3 узла, quorum queues) + API Gateway (скелет) | Любой модуль может подключиться к шине и зарегистрировать маршрут | 1–2 ч/нед | DevOps | Все модули |
| 0.5 | Выбор первой БД для миграции (наименее рискованная из 5+ Oracle) | Зафиксировано решение с обоснованием | 0.5 ч/нед | Архитектор + владелец БД | Раздел 6.3 |

**Итог фазы 0:** есть кластер, шина, gateway, модель данных и понимание, с чего начинать миграцию БД.
Дальше — параллельные независимые треки.

## Пул независимых модулей (после фазы 0, порядок произвольный)

Каждый модуль — свой микросервис/набор сервисов со своим API. Если ресурсов на полноценную
реализацию нет — поднимается заглушка (тот же контракт, упрощённая логика), и модуль
возвращается в работу позже без изменений на стороне потребителей.

| Модуль | Что делает | MVP-статус | Оценка (полная реализация) | Зависимости | Примечание |
|---|---|---|---|---|---|
| **SCADA** | Сбор данных со станков, загрузка оборудования | Решаем по ходу | 4–8 ч/нед | Нужно уточнить парк оборудования (сетевой интерфейс/ЧПУ, возможно OPC UA) | Высокий риск по срокам — начать с аудита оборудования |
| **MES** | Диспетчеризация склад ↔ производство, прослеживаемость | Решаем по ходу | 3–6 ч/нед | Модель сущностей (0.2) | Хороший кандидат для пилота — понятная бизнес-логика |
| **ERP** | Снабжение, планирование, бухгалтерия, табельное бюро | Решаем по ходу | 4–8 ч/нед | Модель сущностей (0.2) | Можно декомпозировать на подмодули (снабжение / бухгалтерия / табель) |
| **CRM** | Работа с клиентами, сводная аналитика для руководства | Решаем по ходу | 3–5 ч/нед | Не блокируется, но полезнее после ERP/MES | Можно стартовать с заглушки, добить последним |
| **Отчётность** | Grafana (операционные дашборды) + Metabase/Redash (управленческие отчёты) | Решаем по ходу, подключается по частям | 1–3 ч/нед | Источники данных из других модулей | Готовые open-source инструменты, не пишем с нуля |
| **Сегментация сети ИТ/OT** | Разделение контура CRM/ERP и цехового OT-контура SCADA | Уточнить требования | 0.5–1 ч/нед | Требования ИБ | Не блокирует старт разработки |
| **Миграция БД (раздел 6.3)** | По одной Oracle-БД, strangler pattern (см. раздел 4 ТЗ) | Начинается после 0.5 | 2–4 ч/нед на БД | Готовность CDC-инфраструктуры | Параллельно с миграцией десктоп-клиентов |
| **Миграция десктоп-клиентов (6.4)** | Замена прямой записи в БД на работу через API, по цехам/участкам | По одному клиенту | 1–3 ч/нед на клиента | Готовность соответствующего модуля | Идёт синхронно с миграцией «своей» БД |

## Рекомендуемая последовательность старта (не жёсткая, но практичная)

1. **Сейчас:** Фаза 0 целиком — без неё некуда подключать модули.
2. **Первый модуль-пилот:** MES или один подмодуль ERP (например, снабжение) — понятная
   логика, быстрая обратная связь, обкатка паттерна «модуль + заглушки соседей».
3. **Параллельно с пилотом:** аудит оборудования для SCADA (долгий срок реакции — чем раньше
   начать уточнять парк станков, тем меньше риск для дорожной карты).
4. **Как только определена первая БД (0.5):** запускать её миграцию по strangler pattern —
   независимо от прогресса по модулям.
5. **Отчётность подключать инкрементально** — сразу после того, как у первого модуля
   появляются данные в шине/БД, не дожидаясь всех источников.
6. **CRM и сегментация сети ИТ/OT** — по остаточному принципу, не блокируют ничего.

## Открытые вопросы (нужно решить до/во время фазы 0)

- Парк оборудования для SCADA: сетевые интерфейсы, ЧПУ, потребность в OPC UA.
- Требования ИБ к сегментации сети ИТ/OT.
- Приоритет первой Oracle-БД для миграции (задача 0.5).
- Выбор конкретного BI-инструмента для управленческой отчётности (Metabase vs Redash vs свой сервис).
